# Futures Reconstruction

This document records NanoClaw's working futures map. It is a lightweight
research surface, not a prediction market or legal/business plan.

The method is simple:

1. read public signals from the open-source and agent ecosystems;
2. reconstruct the forces behind them;
3. state several probabilistic scenarios;
4. turn the scenarios into small, reviewable repository actions.

## Public Signals

- GitHub's 2025 Octoverse reported record open-source activity, rapid AI
  repository growth, and AI infrastructure among the fastest-growing project
  categories.
- GitHub is positioning the platform as an "Agent HQ" where multiple coding
  agents can be assigned, reviewed, and coordinated through normal GitHub
  workflows.
- MCP and related agent tool protocols are moving from novelty into shared
  infrastructure.
- Public agent indexes and safety surveys show a gap between capability
  benchmarks and safety disclosure.
- Open-source maintainers are seeing both useful AI contributions and noisy
  AI-generated reports, so trust, review quality, and small scoped work matter.

## Seven Probabilistic Scenarios

Probabilities are subjective planning weights for the next 12-24 months. They
do not need to sum to 100 percent because several scenarios can happen at the
same time.

| Scenario                                                         | Probability | Reconstruction                                                                                                                                 | NanoClaw response                                                                                         |
| ---------------------------------------------------------------- | ----------: | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Local agent workspaces become normal                             |         70% | More users will want agents that can touch files, messages, and schedules, but they will also want an inspectable boundary around that access. | Keep the base runtime small, document mounts, and make safety review part of setup.                       |
| GitHub becomes a coordination layer for agents                   |         65% | Issues, pull requests, reviews, discussions, and releases are becoming the public control surface for asynchronous agents.                     | Use issues as a public work log, keep releases crisp, and invite narrowly scoped feedback.                |
| Safety disclosure becomes a trust signal                         |         60% | Projects that explain credentials, mounts, review points, and failure modes will be easier to trust than projects that only show demos.        | Maintain `SAFETY_MODEL.md`, keep examples fake, and add tests around credential behavior.                 |
| Skills replace broad feature bloat                               |         55% | Personal automation systems become more useful when capabilities are optional, auditable, and fork-local.                                      | Prefer skills-as-branches and optional docs over large base features.                                     |
| AI-generated contribution noise increases                        |         55% | Maintainers will face more low-context issues, PRs, and security reports generated by agents.                                                  | Contribute in small, human-readable patches and ask one precise question at a time.                       |
| Open-source funding gets more explicit                           |         45% | More projects will publish sponsor criteria and annual pledge reports as infrastructure maintenance becomes visible.                           | Track sponsorship candidates, start small, and document why a project receives support.                   |
| Digital exhibitions become credible project artifacts            |         35% | Technical projects will increasingly use curated catalogs, demos, and provenance notes to explain ideas beyond code.                           | Build a separate exhibition kit and collection catalog without mixing rights metadata into code.          |
| Patent/open publication strategy becomes part of project hygiene |         30% | AI-assisted invention will raise more questions about disclosure, authorship, and defensive publication.                                       | Keep publication notes, invention memos, and license choices explicit before publishing high-value ideas. |

## Near-Term Research Questions

- What agent actions should remain suggestion-only even inside a trusted fork?
- Can a public release be useful without encouraging unsafe quick installs?
- Which logs are enough for trust without exposing private user data?
- Where should a skill live: branch, subdirectory, separate repository, or docs
  recipe?
- What would a respectful first sponsorship note look like for a maintainer?
- How should a project publish an AI-assisted idea as open source while
  preserving attribution and rights clarity?
- Can a digital exhibition page become a serious technical artifact rather
  than a decorative landing page?

## Operating Principle

NanoClaw should behave like a careful participant in the ecosystem:

- read before speaking;
- ask narrow public questions;
- publish small artifacts;
- keep safety claims reviewable;
- separate code, collection rights, sponsorship, and invention notes;
- prefer durable public context over private improvisation.

## Next Actions

1. Open one GitHub discussion asking for feedback on the seven scenarios.
2. Use the discussion to collect project suggestions and safety questions.
3. Convert useful feedback into docs, tests, or skills.
4. Revisit the probabilities monthly and record changed assumptions.
